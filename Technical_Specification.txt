DESKTOP BROWSER — TECHNICAL SPECIFICATION
Version: 0.6
Last updated: 2026-11-17
Status: Architecture decisions and requirements; implementation has not started.

============================================================
1. PROJECT GOAL
============================================================

Build a fast, lightweight Windows desktop browser, prioritizing low-end
computers while preserving modern website compatibility, security,
and stability.

Primary goals:
- Fast application startup and page loading.
- Low RAM consumption, including with multiple tabs.
- Low CPU usage during idle and ordinary browsing.
- Efficient network and cache usage, with optional data-saving features.
- Support for modern web standards and JavaScript.
- Maintain security and stability through engine updates.

"Fastest browser" is not a claim until demonstrated by repeatable
comparative benchmarks.

============================================================
2. TARGET PLATFORM AND HARDWARE
============================================================

- Operating system: Windows 10 only.
- Architecture: 64-bit (x64) only.
- Windows 11 is outside the current project scope.
- No 32-bit build is planned.
- Prioritize very low-end processors and computers.
- Minimum design target: 2 GB RAM for basic browsing.

The 2 GB target is not a guarantee that every modern, resource-heavy
website or many simultaneous tabs will run smoothly. Windows and
modern websites also consume substantial memory.

Platform note:
Microsoft ended general support for Windows 10 on 2025-10-14.
The project must account for the security implications and keep the
browser engine and dependencies updated for as long as compatible
security updates are available.

============================================================
3. APPROVED ENGINE AND RUNTIME
============================================================

Approved browser engine: Chromium.
Approved embedding framework: Chromium Embedded Framework (CEF).
Approved CEF runtime: Alloy Runtime.

Architecture:
- Embed Chromium using CEF.
- Use Alloy Runtime.
- Build our own browser interface rather than relying on Chrome's
  built-in browser UI.
- Use C++ for the native Windows application and CEF integration.
- Use native Windows facilities where appropriate for desktop
  integration, windows, menus, and files.
- Build a custom optimization and management layer around CEF.

Rationale:
CEF + Alloy Runtime gives the project a suitable foundation for a
custom desktop browser interface and substantial control over the
browser experience.

Important boundaries:
- We are not building a new rendering engine.
- We are not planning to modify Chromium's internal source code
  at this stage.
- CEF + Alloy is an approved architecture choice, not a proven claim
  that it is lighter or faster than every alternative.
- Track compatible CEF/Chromium releases and establish a security
  update and distribution process.

============================================================
4. HYBRID OPTIMIZATION APPROACH
============================================================

"Hybrid" means one rendering engine (Chromium through CEF) combined
with our own native application and optimization layer.

It does NOT mean embedding multiple browser engines, such as
Chromium and Gecko, in the same browser.

Proposed custom systems:

4.1 Smart Tab Manager
- Manage tab lifecycle and resource use.
- Consider delaying work for tabs that do not need immediate loading.
- Suspend or discard inactive-tab resources when appropriate.
- Restore tabs when the user returns, handling unsaved page state
  carefully.

4.2 Adaptive Memory Manager
- Monitor memory use and system memory pressure.
- Apply graduated memory-saving actions.
- Prioritize low-memory devices, especially 2 GB systems.
- Avoid unnecessary reloads and loss of user work.

4.3 Network Optimizer
- Improve cache usage.
- Offer optional ad and tracker blocking.
- Offer optional data-saving behavior for images, video, and
  background requests.
- Avoid silently breaking normal website functionality.

4.4 Smart Startup
- Display the application interface promptly.
- Initialize engine components in a measured, staged manner.
- Delay nonessential background work where safe.
- Measure window appearance separately from first-page readiness.

4.5 Resource Controller
- Monitor CPU, RAM, and GPU-related resource usage.
- Adapt nonessential work to device capability and current pressure.
- Avoid optimizations that compromise compatibility or security.

4.6 Security Manager
- Preserve Chromium security features, including sandboxing and
  site isolation where supported and appropriate.
- Manage permissions, downloads, and security-sensitive behavior.
- Maintain a defined process for CEF/Chromium security updates.

============================================================
5. FEATURE-PRESERVATION RULE — USER APPROVAL REQUIRED
============================================================

The user must be consulted before any browser feature is removed,
disabled, or deliberately reduced.

Before proposing such a change:
1. Identify the feature and why a change is being considered.
2. Explain the expected performance benefit.
3. Explain compatibility, usability, and security consequences.
4. Offer alternatives that preserve the feature where possible.
5. Wait for the user's explicit approval before removing or disabling it.

This rule applies even when a feature appears resource-intensive.
Prefer optimizing how a feature is implemented before proposing
its removal.

Do not disable sandboxing or site isolation merely to reduce RAM.
Do not use single-process mode as a memory-saving shortcut.

============================================================
6. PERFORMANCE VALIDATION PLAN
============================================================

Build a small CEF + Alloy prototype and measure it on representative
Windows 10 x64 hardware, especially a low-memory device where possible.

Measure:
1. Time until the application window appears.
2. Time until the first page is usable.
3. RAM at idle after the browser settles.
4. RAM with one page and a consistent set of test websites.
5. RAM with 5 and 10 tabs.
6. CPU usage at idle and during browsing.
7. Page-load performance.
8. Download and installed size.
9. Behavior under memory pressure.
10. Stability, compatibility, and practicality of security updates.

Test discipline:
- Use the same device, websites, network conditions, and test steps.
- Record exact CEF/Chromium versions and build settings.
- Repeat measurements; do not rely on a single run.
- Count all browser child processes, not only the main process.
- Compare like-for-like conditions.
- Do not claim CEF is inherently lighter than alternatives
  without measurements.

7. APPROVED BROWSER FEATURE REQUIREMENTS — FIRST RELEASE
============================================================

The user explicitly approved all seven feature groups below as part
of the browser's required feature scope. Every listed item is retained.
No item in this section is to be silently omitted, removed, or treated
as out of scope. Implementation may be planned and delivered in stages,
but staging does not mean cancellation. Any later proposal to remove,
disable, or reduce a feature must follow Section 5 and receive the
user's explicit approval.

7.1 Core Browser Interface
- Address bar that also accepts search queries.
- Back button.
- Forward button.
- Reload button.
- Stop-loading button.
- Home button.
- Create a new tab and close the current tab.
- Display multiple tabs and switch between them.
- Display a page-loading indicator.
- Open links in a new tab or a new window.
- Use a classic rectangular tab design similar to Google Chrome.
- Display each website's favicon in its tab when the website provides
  one; show a default fallback icon when no favicon is available.
- Support Split Screen within a single browser tab, displaying two
  websites side by side in separate page areas within that tab.

7.2 Tab and Window Management
- Open, close, and reorder tabs.
- Duplicate a tab.
- Restore the most recently closed tab after accidental closure.
- Open a new browser window.
- Open a private-browsing (Incognito) window.
- Save and restore tabs when the browser is restarted.
- Provide a list of currently open tabs.

7.3 Search and Websites
- Google as the default search engine.
- Allow the user to change the search engine to Bing or other
  supported search engines.
- Add websites to bookmarks.
- Maintain browsing history.
- Manage bookmarks and browsing history.

7.4 Downloads
- Download files from the internet.
- Display download progress.
- Pause, resume, and cancel downloads.
- Open a file after its download completes.
- Open the folder containing a downloaded file.
- Manage the downloads list.

7.5 Privacy and Security
- Private browsing.
- Manage cookies.
- Clear browsing history and browsing data.
- Control website permissions, including camera, microphone,
  and geolocation.
- Warn users about unsafe websites.
- Preserve Chromium security protections, including sandboxing.

7.6 Settings and Customization
- Choose the home page.
- Choose the search engine.
- Choose the download location.
- Light and dark themes.
- Control font size and page zoom in/out.
- Language settings.

7.7 Performance and Resource Optimization Features
- Intelligent RAM-usage management.
- Suspend inactive tabs when appropriate and safely.
- Manage cache to reduce unnecessary data reloads.
- Reduce background CPU usage.
- Monitor browser resource usage.
- Restore tabs after the browser is closed or crashes.

Implementation and behavior notes:
- These seven groups are all approved requirements, not a list of
  features that may be arbitrarily discarded for a lightweight build.
- Where a feature has configurable behavior, its defaults and controls
  will be specified during detailed design.
- Tab suspension, cache management, and memory-saving actions must
  protect user work and avoid unnecessary reloads.
- Private browsing must not retain ordinary browsing history or
  session data after the private session ends, subject to the detailed
  privacy design.
- Website permission controls and security warnings must be implemented
  without weakening Chromium's security protections.
- The browser must distinguish restoring ordinary sessions from
  restoring private sessions; private session data must not be restored
  as an ordinary session.

## Core Browser Interface — Approved Requirements (2026-11-17)

### 1. Tab appearance
- Tabs shall use a rectangular design similar to Google Chrome.
- A tab shall display the website favicon when one is available.
- A tab shall display the page title and a close control.

### 2. Split Screen within a single tab
- A single browser tab shall be able to display two websites side by side.
- Each side shall have its own independent address/search bar and navigation context.
- The user shall be able to enter a different URL or search query independently in either side.
- The user shall also be able to select an already-open tab as the content for the second side.
- Navigation in one side shall not change the website displayed in the other side.
- The user shall be able to exit Split Screen and return to a single-page view.
- The divider between the two sides shall be draggable to resize both sides freely, including unequal ratios such as 70/30.
- Provide a way to restore an even 50/50 split.
- Preserve the selected split ratio while navigating between websites within that split view.

### 3. Ways to activate Split Screen
All three activation methods are approved:
- A dedicated Split Screen button in the browser toolbar.
- A Split Screen option in the context menu opened by right-clicking a tab.
- Dragging a tab and dropping it into the opposite side of the split view.

These requirements are approved for the browser's planned first release. Do not omit or remove any item without the user's explicit approval.

## Approved UI and Download Manager Decisions (2026-11-17)

### A. Split Screen entry point — updated decision
- The Split Screen command shall be placed inside the browser's Tools menu.
- It shall not occupy a permanently visible position beside the address bar.
- This decision updates and supersedes the earlier proposal for a permanently visible Split Screen toolbar button.
- The other approved activation methods remain:
  - A Split Screen option in the right-click context menu for a tab.
  - Dragging a tab and dropping it into the opposite side of the Split Screen view.
- Keep all previously approved Split Screen behavior: two independent page areas within one tab; independent address/search bars and navigation; selecting an already-open tab for the second side; draggable divider with freely adjustable ratios; a 50/50 reset; preserving the chosen ratio while navigating; and returning to a single-page view.

### B. Download Manager — approved first-release requirements
The Download Manager is a high-priority core feature. All requirements below are approved and must be included:

1. Pause: allow the user to pause an active download.
2. Resume: continue a paused download from the point already downloaded, rather than restarting from zero whenever the server and transfer method support resumption.
3. Repeated Pause/Resume: allow the user to pause and resume the same download repeatedly without losing completed data, subject to server and protocol support.
4. Cancel: allow the user to cancel a download.
5. Retry: allow the user to retry a failed download.
6. Progress information: show download percentage, current speed, estimated remaining time, downloaded amount, and total file size when available.
7. Persistent download list: retain the download list across browser restarts.
8. Resume after restart: allow supported downloads to resume after the browser is closed and reopened, preserving partial data when possible.
9. Multiple downloads: support downloading multiple files concurrently and managing each download independently.

### C. User-selectable download methods
The browser shall support both download methods below, and the user shall choose which method to use:

- **Chunked / multi-connection download:** split a file into multiple parts and download the parts concurrently, then assemble them into the completed file.
- **Standard download:** download the file using a normal single transfer, with Pause/Resume where supported.

The selected method shall be user-controlled; do not force one method for all downloads. The browser shall expose the choice clearly in the download UI or settings and allow the user to change it for a download.

### D. Download compatibility and integrity requirements
- Chunked downloading requires server support for byte-range requests (or another technically valid way to retrieve separate ranges). If unavailable, explain that limitation and use or offer standard downloading; never imply that parallel chunking is guaranteed for every server.
- Pause/resume and resume-after-restart also depend on server support and stable resource identity/validators. Preserve partial data safely and verify that the remote file has not changed before appending resumed data.
- Assemble downloaded chunks in the correct order and verify completion/integrity before marking the file complete.
- Handle interrupted connections, failed chunks, retries, and cancellation without corrupting the final file.
- Do not silently switch the user's chosen download method; if the chosen method is unsupported, notify the user and request or apply only a clearly disclosed fallback policy.

All items in this section are approved requirements for the planned first release. Do not omit, silently downgrade, or remove any item without the user's explicit approval.

### E. Download Manager progress display — approved visual behavior
- Each file shall appear as one download item/row in the downloads list, regardless of how many internal chunks or connections are used.
- For chunked downloads, show the internal chunks visually within that same download item, following the ADM-style segmented progress presentation agreed with the user.
- Show a separate progress indicator for each internal chunk so the user can see the progress of the individual parts.
- Do not present the chunks as separate files or separate top-level download entries.
- Clearly identify the selected method as either **Chunked / Multi-connection** or **Standard / Single connection**.
- For standard downloads, show a single overall progress indicator rather than multiple chunk indicators.
- Keep the overall file progress, downloaded/total size, speed, and estimated remaining time visible where available.
- Provide Pause, Resume, Cancel, and Retry controls for the overall file download; the user controls the complete download as one operation.
- The agreed visual reference is the ADM-style presentation shown in the conversation: one file item with its overall progress and visible internal segment progress in the same item. Do not replace this with a separate list of chunk downloads or a different presentation without the user's approval.


## Startup Behavior — Approved Decision (2026-11-17)

- When the browser starts, open the configured Home Page only.
- Do not automatically restore the tabs or windows that were open when the browser was last closed.
- This is the user's explicit startup preference and supersedes any earlier generic wording that implied automatic session restoration at startup.
- This decision changes the automatic startup behavior only. It does not authorize removing other approved tab-management or session-related capabilities. Any separate manual session-recovery behavior, including how saved sessions may be accessed, remains to be specified; do not assume it is removed or automatically enabled.

## Home Page and Startup Behavior — Approved Decisions (2026-11-17)

### Built-in Home Page
- The browser shall provide its own built-in Home Page; it is not merely a user-supplied website URL.
- The page shall include a prominent search box and website shortcuts.
- Keep the design familiar and simple, similar to the ordinary start pages users expect in mainstream browsers.
- Prioritize fast display, low memory use, and low CPU overhead. Avoid unnecessary animations, heavy effects, and nonessential background work.

### Startup
- On a normal browser launch, open the configured Home Page only.
- Do not automatically restore the tabs or windows that were open when the browser was last closed.
- This changes automatic startup behavior only; it does not authorize removing other approved tab-management or session-recovery capabilities. Crash-recovery behavior and any separate manual session-recovery option remain to be specified.

## Technical Architecture — Selected Stack (2026-11-17)

The following technology choices are selected for the Windows 10 x64 desktop browser, prioritizing a complete browser experience, low resource use, security, maintainability, and compatibility with low-end devices.

### Core Browser Architecture
- Browser engine: Chromium, integrated through the Chromium Embedded Framework (CEF).
- CEF integration model: use the modern Chrome Bootstrap. Use Alloy Style only where required for the custom native-window integration; do not use the deprecated Alloy Bootstrap.
- Browser host and application logic: native C++.
- Native user interface: Win32 API. Do not introduce Qt or another heavyweight UI framework for the first release.
- Native drawing: use Windows-native drawing facilities where appropriate (Direct2D/DirectWrite for custom-drawn UI elements); avoid unnecessary visual effects and continuously animated UI.
- Keep Chromium's multi-process architecture, Sandbox, and Site Isolation enabled. Do not use single-process mode or disable security features to reduce memory.

### Build and Development Toolchain
- Compiler/toolset: MSVC from Visual Studio 2022, using a CEF-compatible toolset and Windows SDK version for the selected CEF branch.
- Build configuration: CMake.
- Build executor/generator: Ninja for the application build where appropriate.
- Language baseline: modern C++ supported by the selected CEF distribution and MSVC toolset; prefer C++20 for application-owned code only where it does not conflict with CEF requirements.
- Use official CEF binary distributions for application development and integration. Do not build/fork all of Chromium from source unless a demonstrated requirement makes it necessary.

### Local Data and Configuration
- Embedded database: SQLite for bookmarks, browsing history, download records, and structured browser metadata.
- Lightweight configuration: JSON for simple preferences and settings; do not use a database for every small setting.
- Store user data in the appropriate Windows per-user application data directory, separate from the installation directory.

### Testing, Diagnostics, and Reliability
- Unit tests: GoogleTest for application-owned C++ logic.
- Browser integration tests: automated CEF-based test harness and ChromeDriver where supported, plus real-site manual regression tests.
- Performance diagnostics: Windows Performance Toolkit (WPR/WPA), Windows process/memory diagnostics, and Chromium/CEF tracing and diagnostics.
- Crash diagnostics: use Chromium/CEF-supported crash reporting facilities where available; never collect or transmit crash data without a clear privacy policy and user disclosure.
- Establish repeatable performance tests on low-end hardware, including the 2 GB RAM design target. Treat the target as a test requirement, not a guarantee that every modern website will run smoothly in 2 GB.

### Resource and Security Policies
- Prioritize fast cold start, low idle CPU usage, bounded background work, and memory-aware tab lifecycle management.
- Preserve browser compatibility and security before attempting memory reductions. Any memory-saving behavior must be measured for impact on active pages, media, downloads, and session state.
- Keep hardware acceleration enabled by default where supported, with graceful fallback for problematic or older graphics drivers; validate both accelerated and fallback paths.
- Maintain a documented CEF/Chromium security-update process and regularly move to supported security-patched CEF branches.

### Explicitly Excluded
- Do not implement system-wide internet blocking or control of other applications' network access. This idea was withdrawn by the user and is not part of the product scope.
- Do not add Qt to the first-release UI stack unless later evidence demonstrates a compelling need and the user approves the change.
